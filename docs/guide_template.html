Build a Recruiter Assistant Agent

A practice project: match a job description (JD) to a resume with an explainable score, and shortlist a whole folder of resumes from Google Drive. You build and test locally first, then deploy to AWS with Docker, CI/CD (GitHub Actions) and ECS Fargate, using the cheapest options and no scaling.

1. Architecture and cost choices

Browser UI (static HTML)  -->  FastAPI (one container)
                                  |-- parse PDF/DOCX/TXT
                                  |-- anonymize (blind screening)
                                  |-- embed chunks (fastembed, runs in-process)
                                  |-- ChromaDB (in-memory vector DB) -> retrieve best evidence per JD requirement
                                  |-- Google Drive API (service account)
                                  `-- score = 60% semantic match + 40% required-skill coverage
DecisionWhy (cost / simplicity)
Embeddings: fastembed + bge-small (local ONNX)No paid embedding API, no GPU, small image.
Vector DB: ChromaDB in memoryNo database service to pay for; resumes are re-indexed per request, which is fine at practice scale.
No LLM in the scoring pathCheaper, deterministic and auditable (every score has evidence); easier to defend as unbiased.
UI served by the same FastAPI containerOne image, one ECS service. The same UI works locally and on AWS (it calls relative URLs).
Fargate 0.5 vCPU / 1 GB, 1 task, public IPNo load balancer and no NAT gateway (the two biggest hidden costs). Access is limited to your IP by a security group.
Secret in SSM Parameter Store (SecureString)Free tier, unlike Secrets Manager.

How scoring works: the JD is split into requirement lines. Each resume is anonymized, chunked and stored in the vector DB. For every JD requirement we retrieve the most similar resume chunk (RAG retrieval) and turn the cosine similarity into 0-1. The semantic score is the average across requirements. Skill coverage is the share of skills named in the JD (from a vocabulary in scoring.py) found in the resume. The UI shows the evidence excerpts so a recruiter can verify every score.

3. Google Drive authentication (service account)

A service account is a robot Google identity. It needs no browser login, so the same method works locally and on AWS.

  1. Open Google Cloud Console, create a project, then APIs & Services > Library > Google Drive API > Enable.
  2. IAM & Admin > Service Accounts > Create. Open it, go to Keys > Add key > JSON, and save the file as secrets/sa.json (it is git-ignored; never commit it).
  3. Copy the service account's email (...@...iam.gserviceaccount.com).
  4. In Google Drive, right-click the resume folder for a JD, choose Share, add that email as Viewer.
  5. Copy the folder link. Recruiters paste this link in the UI together with the JD.

The scope is drive.readonly, so the agent can never modify files. Each JD has its own folder; only folders explicitly shared with the robot are readable.

5. Run and test locally

pytest -q                              # first run downloads the ~130 MB embedding model
uvicorn app.main:app --reload --port 8000
  1. Open http://localhost:8000.
  2. Paste the text of sample_data/jd_python_backend.txt (or upload it).
  3. Source: local:jd_python_backend, press Shortlist. Expected order: candidate_a, candidate_b, candidate_c.
  4. Google test: set the source to your shared Drive folder link and repeat.
  5. Single match: upload one resume under "Match a single resume".

Or call the API directly:

curl -F "jd_file=@sample_data/jd_python_backend.txt" -F "source=local:jd_python_backend" http://localhost:8000/api/shortlist
If the first request seems slow, that is the embedding model loading into memory once per process. Troubleshooting: "Could not read resumes: 404" means the folder is not shared with the service-account email; "No extractable text" means a scanned PDF.

The model is baked into the image at build time, so the container starts without downloading anything. Sample resumes are copied into the image for the demo; for real use mount a folder (as the compose file does).

7. Fairness and compliance design

  • Blind scoring: identity and protected-attribute signals are removed before embedding and scoring (section 4.2). Scores depend only on skills and described work.
  • No age proxies: years are stripped; "years of experience" and graduation dates are deliberately not scored.
  • Explainable: each score lists matched/missing skills and resume excerpts, so a recruiter can audit it.
  • Human in the loop: the tool shortlists for review and never rejects; the UI says so on every result.
  • JD wording check: biased phrases in the JD are flagged.
  • Privacy: resumes are processed in memory and not stored; the Drive scope is read-only; logs contain no resume text.
Limits to be honest about: anonymization by pattern matching is not perfect (e.g. unusual date formats, school names or clubs can still hint at identity); embeddings can carry bias from their training data; and the skill vocabulary favors tech roles. Before using this on real candidates, test it on diverse resumes, keep an audit log, and check applicable rules with legal counsel (for example, India's DPDP Act, the EU AI Act which treats recruitment AI as high-risk, and bias-audit laws such as New York City Local Law 144). This tutorial is not legal advice.

8. Deploy to AWS (ECS Fargate)

8.1 Prerequisites

  • AWS account with a billing alarm set (Billing > Budgets, e.g. a few dollars).
  • AWS CLI v2 configured: aws configure (use an IAM user with admin rights for this one-time setup; region ap-south-1).
  • Docker running, and secrets/sa.json present.

8.2 One-time infrastructure

This script creates the ECR repo, log group, ECS cluster, execution role, the SSM secret from secrets/sa.json, and a security group that allows port 8000 only from your current IP.

{{file:infra/setup-aws.sh}} 
./infra/setup-aws.sh

8.3 First image push

export REGION=ap-south-1 ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $ACCOUNT.dkr.ecr.$REGION.amazonaws.com
docker build --platform linux/amd64 -t recruiter-agent .
docker tag recruiter-agent:latest $ACCOUNT.dkr.ecr.$REGION.amazonaws.com/recruiter-agent:latest
docker push $ACCOUNT.dkr.ecr.$REGION.amazonaws.com/recruiter-agent:latest

--platform linux/amd64 matters on Apple Silicon Macs because Fargate runs x86 here.

8.4 Register the task definition

{{file:infra/task-def.json}} 
sed -e "s/ACCOUNT_ID/$ACCOUNT/g" -e "s/REGION/$REGION/g" infra/task-def.json > /tmp/td.json
aws ecs register-task-definition --cli-input-json file:///tmp/td.json --region $REGION

The Google key is injected as an environment variable from SSM, so it is never baked into the image.

8.5 Create the service (one task, public IP)

VPC=$(aws ec2 describe-vpcs --filters Name=isDefault,Values=true --query 'Vpcs[0].VpcId' --output text --region $REGION)
SUBNETS=$(aws ec2 describe-subnets --filters Name=vpc-id,Values=$VPC --query 'Subnets[].SubnetId' --output text --region $REGION | tr '\t' ',')
SG=$(aws ec2 describe-security-groups --filters Name=group-name,Values=recruiter-agent-sg --query 'SecurityGroups[0].GroupId' --output text --region $REGION)
aws ecs create-service --cluster recruiter-cluster --service-name recruiter-service \
  --task-definition recruiter-agent --desired-count 1 --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[$SUBNETS],securityGroups=[$SG],assignPublicIp=ENABLED}" \
  --region $REGION

8.6 Open the app

TASK=$(aws ecs list-tasks --cluster recruiter-cluster --service-name recruiter-service --query 'taskArns[0]' --output text --region $REGION)
ENI=$(aws ecs describe-tasks --cluster recruiter-cluster --tasks $TASK --region $REGION --query "tasks[0].attachments[0].details[?name=='networkInterfaceId'].value" --output text)
aws ec2 describe-network-interfaces --network-interface-ids $ENI --region $REGION --query 'NetworkInterfaces[0].Association.PublicIp' --output text

Browse to http://THAT_IP:8000. Paste a JD and a Drive folder link, exactly as you did locally. If it does not load: check the task is RUNNING (aws ecs describe-services), view logs in CloudWatch group /ecs/recruiter-agent, and make sure your IP did not change (re-add it to the security group).

This setup is HTTP-only and reachable only from your IP, which is acceptable for practice with sample data. Do not load real candidate data this way. For real use you would add an Application Load Balancer with HTTPS (ACM certificate) and login (for example Cognito), which costs extra.

9. CI/CD with GitHub Actions

On every push to main: run tests, build the image, push it to ECR tagged with the commit SHA, render the task definition with the new image, and deploy to ECS, waiting for stability.

  1. Create a GitHub repo and push the project (secrets and .env are git-ignored).
  2. Create the deploy role using OIDC (no long-lived AWS keys in GitHub): 
    ./infra/github-oidc.sh YOUR_GITHUB_USER/YOUR_REPO
  3. In GitHub: Settings > Secrets and variables > Actions > New secret, name AWS_ROLE_ARN, with the ARN the script prints.
  4. Push a small change to main and watch the Actions tab.
{{file:infra/github-oidc.sh}} {{file:.github/workflows/deploy.yml}}

Note: each deployment starts a new task, so the public IP changes; re-run the lookup in 8.6.

10. Cost control and cleanup

A single small Fargate task costs a few cents per hour while running; ECR, logs and SSM are negligible at this size. Pause when you are not practicing:

aws ecs update-service --cluster recruiter-cluster --service recruiter-service --desired-count 0 --region $REGION   # pause
aws ecs update-service --cluster recruiter-cluster --service recruiter-service --desired-count 1 --region $REGION   # resume

Delete everything when done:

aws ecs delete-service --cluster recruiter-cluster --service recruiter-service --force --region $REGION
aws ecs delete-cluster --cluster recruiter-cluster --region $REGION
aws ecr delete-repository --repository-name recruiter-agent --force --region $REGION
aws logs delete-log-group --log-group-name /ecs/recruiter-agent --region $REGION
aws ssm delete-parameter --name /recruiter-agent/google-sa --region $REGION
aws ec2 delete-security-group --group-id $SG --region $REGION
